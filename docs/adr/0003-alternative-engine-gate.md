# ADR 0003: ворота решения для альтернативного движка (Unity/Godot/Unreal)

## Статус

Принято

## Контекст

`app/` реализует целевой продукт как **десктоп-приложение** (Electron + React + Three/R3F) с высокой визуальной планкой. При росте требований к рендеру/ассетам и сложных фичах (LOD, отражения, GLB-пайплайн) естественно возникает вопрос: «а не перейти ли на другой движок?».

Этот вопрос опасен без формализованных критериев:

- можно преждевременно “сжечь” месяцы на миграцию вместо улучшения текущей реализации;
- можно потерять single source of truth для логики мира/NPC/нарратива;
- можно деградировать качество сборки/UX (особенно вокруг локального ИИ, сохранений, UI-панелей).

## Решение

Вводим **ворота решения**: альтернативный движок рассматривается **только** как отдельное архитектурное решение после достижения явных критериев. До прохождения ворот **не начинаем** миграцию, не дублируем системы и не вносим изменения “под будущую миграцию” без нужды.

### Когда ворота считаются пройденными

Должны выполняться **все** пункты:

1. **Измеримый перф-упор**: есть воспроизводимые профили (GPU/CPU) и доказано, что лимит не снимается оптимизациями в текущем стеке (LOD, batching, пресеты качества, отражения, стриминг ассетов) при приемлемом бюджете разработки.
2. **Стабильный контракт домена**: ключевые домены (`domain/**`, `types/game.ts`) и сохранения стабилизированы (ADR/тесты), чтобы новая реализация не стала «переписыванием игры заново».
3. **Пайплайн ассетов**: сформулирован и протестирован пайплайн моделей/LOD/материалов (минимум: `public/models/` + бюджеты + деградации по tier), и ясно, что текущие ограничения связаны с движком/рантаймом, а не отсутствием пайплайна.
4. **План поставки**: определён целевой канал поставки (Windows `.exe`), совместимость с локальным ИИ/IndexedDB/сейвами, и есть план “как не потерять UX”.

### Что делаем до прохождения ворот (в рамках текущего стека)

- Поддерживаем и улучшаем существующий рендер (LOD, тени по tier, отражения воды, GLB-подключение).
- Держим доменную логику независимой от UI/рендера.
- Сохраняем `orchestrate:gate` зелёным на каждом инкременте.

## Последствия

- Решение о миграции станет **редким и осознанным**, а не рефлексом на очередной “сложный” таск.
- Улучшения в `app/` не будут «временными» и не потребуют скрытого TECH_DEBT “под будущий движок”.
- Если ворота будут пройдены — появится чёткая база для нового ADR о выборе движка и стратегии миграции (без переписывания домена).
